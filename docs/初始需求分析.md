# 初始需求分析

状态：已确认，作为开工时的需求基线。  
目的：冻结开工时的问题和范围。后面加功能时先对照本文，避免把后加的广场、更新日志倒写成原始需求。  
配对文档：《方案设计》。本文第 6 节的补充已纳入方案设计。

## 1. 问题

备考计算机二级时，一门 B 站课总长约 18 小时。每天还要上课，能听课的时间只有 2 小时，也就是 120 分钟。每一集时长不齐，120 分钟经常落在某一集的中间。用户要自己算出「今天看到第几集的第几分钟」，把这句话发到微信，第二天再从那里接着看。

要省掉的是每天的手工加法和手工记录，不是把视频搬到自己的网站上播放。

## 2. 用户与场景

1. 第一用户就是作者本人：学生，时间被课表切碎，手机和电脑都会打开网站。
2. 同样的人：手里有一门很长的 B 站课，每天只有固定的几十分钟到两小时。
3. 使用时刻有两个：开始一门课时生成整张课表；每天学完后标一下今天学到哪，第二天打开就能续上。

## 3. 第一版必须做到

1. 粘贴 B 站链接，得到这门课的分集和每集时长。
2. 按每天可用分钟数，把整门课切成第 1 天、第 2 天……
3. 某一天的时间在一集中间用完时，写明看到这一集的第几分钟。
4. 手机上能完成粘贴、生成、查看今天该看哪里。
5. 进度按人分开保存。换一天、换设备，还能知道上次看到哪。
6. 有一处可以提交反馈，后面的功能从反馈里长出来。

## 4. 第一版明确不做

1. 不在网站里播放或下载视频。看视频仍回 B 站。
2. 不接网盘和其他视频站。
3. 不调用大模型。时长是确定的，切分用规则。
4. 不收费，不做会员额度。
5. 不做社区广场、版本更新墙。那是后来的功能，不属于这份初始需求。

## 5. 你的三点判断（原文保留）

1. 界面要让人愿意付钱，突出实用，而不是做成华丽展示站。
2. 需要后端。每个人的进度不同，所以需要数据库。
3. 课程信息站在现成开源项目上拿，不自己从零扛解析风险。你点名的工具是 yt-dlp。

## 6. 已补进需求的内容

1. 未登录可以生成课表。登录只为了把进度存进数据库。
2. 每天的默认可用时间是 120 分钟，来自上面的真实场景，用户可以改。
3. 生成结果要能代替那条微信记录：今天看哪些集，若截断则写到第几分钟。
4. 「删除不想学或已经学过的分 P」和「合集 vs 一整门多 P」记为已听到的需求，等反馈验证后再做，不放进第一版承诺。
5. 这个项目要演示的开发方式是：从一个自己的麻烦出发，危险的数据获取借用成熟项目已经走通的办法，先做一个薄的全栈网站，再只按反馈加功能。

## 7. 做成的标准

1. 以 18 小时、分集时长不齐的一门课为例，填入每天 120 分钟，一次生成全部天数。
2. 用户不用心算，就能读出某一天结束在第几集的第几分钟。
3. 手机宽度下，粘贴、生成、看到当天任务，都不需要左右滑动找按钮。
4. 两个账号的进度互不可见。
