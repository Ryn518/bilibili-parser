# DayPlan 技术实现总结

配对文档是《网站功能总结》。本文说明这些功能现在是怎么实现的，方便以后改代码时知道该动哪一层。

版本 **v2.3.0**。运行时是一个 Next.js 应用，没有单独的 Python 服务。

---

## 1. 代码怎么摆

| 位置 | 职责 |
|------|------|
| `app/` | 页面和接口。页面在 `app/**/page.tsx`，接口在 `app/api/**/route.ts` |
| `frontend/` | 浏览器里的组件、页面状态、课表算法 |
| `backend/` | 只在服务器上跑的逻辑：解析 B 站、登录、广场、更新、同步 |
| `data/` | 服务器本机文件。被 Git 忽略 |
| `docs/` | 说明文档 |

路径别名：

- `@/components/*` → `frontend/components/*`
- `@/hooks/*` → `frontend/hooks/*`
- `@/lib/*` → `frontend/lib/*`
- `@/lib/server/*` → `backend/*`

Tailwind 只扫描 `app/` 和 `frontend/`。新组件必须放在这两个目录里，否则样式类不会生成，页面会挤成一行。

线上进程由 PM2 管理，名字是 `kebiaoplan`，目录是 `/var/www/plan`，Nginx 把域名转到本机 3000 端口。

## 2. 技术架构

整个站点是一个 Node 进程。Next.js 14 同时负责页面和接口，没有单独的前端工程，也没有 Python 或 Express 服务。

浏览器只和本站的 `/api` 说话。接口文件很薄，真正的逻辑在 `backend/`。服务器再按需要去访问三处外部东西：B 站公开接口、PostgreSQL、本机 `data/` 目录。

```text
浏览器（React）
    │  fetch /api
    ▼
Next.js 接口（app/api）
    │
    ▼
backend/
    ├── B 站公开接口        解析课程
    ├── PostgreSQL          账号和课表
    └── data/*.json         广场、更新、悄悄话
```

### 前端

前端是 React 18，用 Next.js 的 App Router。`app/` 里的页面只负责把对应组件挂出来，交互都在 `frontend/components/` 的客户端组件里。样式用 Tailwind。

课表切分在浏览器里完成，不在服务器上算。用户改每天分钟数、倍速或排除某一集时，只重算本地数据。

浏览器里存三类东西：

| 位置 | 存什么 |
|------|--------|
| `localStorage` | 登录会话、已保存的课表和打卡进度。登录后按用户名分开 |
| `sessionStorage` | 输入框草稿、刚解析过的课程、当前打开的是哪一门 |
| 内存 | 粘贴进来、还没上传的图片 |

未登录也能规划，这一次的课表留在当前标签页。登录成功后，再把这次结果并进该账号。

请求都打到同源的 `/api`。需要登录的接口带 `Authorization: Bearer <token>`。

### 后端

每个接口是 `app/api/**/route.ts` 里的一个函数，只做三件事：读参数、调用 `backend/` 里的函数、把结果写成 JSON。成功时 `code` 为 `0`。

| 接口 | 做什么 |
|------|--------|
| `/api/bilibili` | 解析链接，向 B 站要课程结构 |
| `/api/auth` | 注册、登录、读取当前登录状态 |
| `/api/sync` | 登录用户的课表上传和下载 |
| `/api/plaza`、`/api/updates`、`/api/feedback` | 广场、更新、悄悄话 |
| `/api/plaza/inbox` | 当前用户收到的赞、评论和回复 |
| `/api/health` | 进程是否还活着 |

B 站请求、密码校验、文件读写都在 `backend/`，不会被打进浏览器包。

### 数据库

数据库是 PostgreSQL。连接库是 `postgres` 这个 npm 包，连接串来自环境变量 `DATABASE_URL`。本机地址不走 SSL，其他地址要求 SSL。连接池最多 1 条，因为线上只有一个 PM2 进程。

没有单独的迁移工具。第一次有人注册或同步时，`backend/db.ts` 里的 `ensureSchema` 执行 `CREATE TABLE IF NOT EXISTS`，把表补齐。

三张表：

| 表 | 存什么 | 主键 |
|----|--------|------|
| `users` | 用户名、密码盐、密码哈希 | `id`（UUID） |
| `user_courses` | 一门课的标题、封面、每天分钟数、打卡日期、整张课表快照 | `user_id` + `bvid` |
| `user_settings` | 最近一次规划缓存、已关闭的「继续学习」提示 | `user_id` |

课表快照和打卡日期用 JSON 字段存，不拆成「每一天一行」。这样前端整包上传，打开时也能整包还原。

同步方式：登录后先把云端课表拉下来，和浏览器里的进度按更新时间合并。之后浏览器把该用户的全部课表再写回去。写的时候放在一个事务里，先删掉这个用户的旧课表行，再插入现在的行，避免留下已经删掉的课。

广场、更新、悄悄话不进这三张表，继续写在服务器的 `data/` 目录。没有配置 `DATABASE_URL` 时，注册用户退回到 `data/users.json`，课表只留在浏览器里。

## 3. 一次规划怎么走完

用户在首页粘贴链接后，浏览器调用 `fetchCourse`，请求 `/api/bilibili?type=course`。

服务器只向 B 站打一次视频详情：

`https://api.bilibili.com/x/web-interface/view?bvid=...`

这次返回里就有标题、封面、分 P，以及合集 `ugc_season`。合集里每一门课的封面在 `arc.pic`，每一集的标题和时长在 `pages`。不下载视频，也不调用 yt-dlp。yt-dlp 只用来对照过该请求哪个公开接口。分 P 列表缺失时，才再请求 `pagelist`。

`b23.tv` 短链先在服务器上展开成 BV 号。

同一条 BV 的解析结果在服务器内存里缓存 30 分钟，浏览器里也有一份短缓存。缓存未命中时才限流：每个 IP 每分钟最多 12 次、每 10 分钟最多 40 次，全站打向 B 站的请求至少间隔 1 秒。B 站返回 412、429 或 503 时，冷却 30 秒。

课表切分在浏览器里，文件是 `frontend/lib/planner.ts`。按分集顺序往当天剩余秒数里装。装得下就整集看完，装不下就从这一集的某一秒拆开，明天接着看。倍速把「墙上的分钟」换成能看的视频秒数。目标天数则先用总秒数倒推出每天分钟数，再走同一套切分。

改时长、倍速或排除某些集时，前端用剩下的分集重算，不重新请求 B 站。

## 4. 一条链接里有多门课

408 这类课程在 B 站里常常是一个合集、一节「正片」，下面挂着多门课。每门课自己又是一个多分 P 视频。

`backend/bilibili-proxy.ts` 里的 `readSeason` 用这个规则区分：

- 合集里至少有两条视频，而且它们各自的 `pages` 超过 1 页：按每一门课拆开，让用户选。
- 普通合集：每一集就是一讲，合成一门课直接排。
- 只有一条视频：走原来的分 P。

用户选完后，`frontend/lib/season-course.ts` 的 `courseFromSections` 裁出要排的分集。只选一门时，课程标题和封面用这一门的；选多门时，标题和封面用总合集的。

保存时不能只用原来的 BV 号当主键，否则后选的一门会覆盖先选的一门。只选一部分时，存储 id 是 `原BV号::课的id`。页面上仍只显示原来的 BV 号。全部都选时，继续用原来的 BV 号。

## 5. 登录和课表同步

密码用 `scrypt` 加盐后存进数据库。登录成功后发一枚 HMAC 签名的 token，密钥是 `AUTH_SECRET`。token 里带用户名、角色和过期时间。之后的请求带这枚 token，服务器验签，不再查密码。

管理员的登录名来自环境变量 `ADMIN_USER`。比较时忽略大小写，页面上显示环境变量里的原始写法。角色写在 token 里。

没有配置 `DATABASE_URL` 时，账号退回到本机 `data/users.json`。线上配置了数据库，注册用户和课表都在 PostgreSQL。课表表是 `user_courses`，每个用户的每条课表一行，主键是用户 id 加上面的存储 id。

浏览器里的进度通过 `/api/sync` 和数据库对齐。从「我的课程」打开时，优先用保存下来的课表快照，不重新解析 B 站。快照丢失时才用原链接重建。

## 6. 广场、更新、悄悄话

这三块的正文都是服务器上的 JSON 文件，图片是旁边目录里的文件。Git 不跟踪 `data/`。

| 数据 | 文件 |
|------|------|
| 广场 | `data/plaza.json`、`data/plaza-images/` |
| 更新 | `data/updates.json`、`data/update-images/` |
| 悄悄话 | `data/feedback.json` |

图片由浏览器粘贴。不超过约 2.4MB 的 PNG、JPEG、WebP 保持原文件。更大的先在浏览器里缩小后再上传。服务器只接受这三种图片的 data URL，单张不超过约 3MB，最多 4 张，写到上面的目录后返回 `/api/.../image?name=`。

广场发帖有频率限制，大约每人每小时 8 条。删除帖子、评论或更新前，前端先弹出确认框。

评论可以再被回复。新评论带 `parentId` 和 `replyTo`。展示时收成两层：主评论下面一条竖线，回复不再套卡片。底部输入框只发主评论。删一条评论时，挂在它下面的回复一起去掉。

赞和评论会进收件箱。`listPlazaInbox` 收集三种事：别人赞了你的帖、别人评论了你的帖或回复了你的评论、别人赞了你的评论。接口是 `GET /api/plaza/inbox`。顶栏铃铛用 `localStorage` 的 `bili-inbox-seen` 记住上次看到哪一条，比这个时间新的算未读。「我的」里的「收到的互动」读的是同一份列表。

新更新提示在全站外壳里请求 `/api/updates?latest=1`。看过的更新 id 记在 `localStorage` 的 `bili-planner-update-invite`。人已经在 `/updates` 时不弹。

悄悄话的联系方式必填。广场新帖、广场评论、更新评论和悄悄话，在配置了 `FEEDBACK_PUSHPLUS_TOKEN` 时通过 PushPlus 推到手机。没有这个变量时，内容照常保存，只是不推送。

输入框草稿用 `useDraftState`。文字写在 `sessionStorage`，图片只留在内存里，避免超出浏览器配额。换页面时组件会卸载，所以不能只靠组件自己的状态。

## 7. 部署时会动什么

服务器上的顺序是：`git pull`、`npm install --legacy-peer-deps`、`npm run build`、`pm2 restart kebiaoplan`。

这次部署会换掉代码和构建结果。不会删除 `data/`，也不会改 `.env` 里的 `DATABASE_URL` 和 `AUTH_SECRET`。本机 `data/` 里的帖子和更新不会跟着 Git 到服务器。

健康检查是 `GET /api/health`，正常返回 `{"ok":true}`。
